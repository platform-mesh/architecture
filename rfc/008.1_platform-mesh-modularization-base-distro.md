## Context

RFC 008 restructures Platform Mesh as a set of composable modules and organized into layers and this proposal takes the next step: enabling third parties to build opinionated distributions on top of a stable, minimal core.

#### Platform Mesh Base Layer as Operating System 

Define a Platform Mesh Base Layer — a minimal, stable, versioned core and a Distributions Model that formalises how adopters package, extend, and ship their own Platform Mesh-based products.

## Base Layer 

| Component | Scope |
|---|---|
| kcp, core APIs + operators | APIs as contract eg marketplace API, metering API, .., isolation |
| Base Helm chart | Minimal installable unit — no UI, no auth assumptions |
| Conformance tests | What a valid Platform Mesh installation must satisfy |

The base layer makes **no assumptions** about auth stack, portal, deployment tooling, or observability.


## Distributions Model

A distribution is a versioned, opinionated packaging of the base layer plus additional components targeting a specific audience or use case.

For example:
```
Platform Mesh Base Layer
    ├── Distro: UI (Base Layer + MFP-based portal) 
    ├── Distro: UI+ReBAC (UI + OpenFGA + Keycloak) 
    ├── Distro: Sovereign Gov (BSI-compliant)
    └── Distro: Industrial Edge (OT/IT bridge, Bosch-pattern)
```

Each distribution owns its own release cadence, extension components, and support model. Contributions flow in two directions: distros contribute extensions upstream to the base layer; the base layer team stabilises and ships contract changes with backwards compatibility guarantees.

---


## Pros

- **Adoption unlock.** Enterprises adopt by building a distro, not by taking Platform Mesh as-is. Removes the "doesn't fit our stack" objection.
- **Ecosystem growth.** Official distributions replace forks. Contributors stay inside the project.
- **Team clarity.** Base layer owner has a narrow, stable mandate. Distribution owners move fast without breaking the core.
- **Brownfield compatible.** The base layer installs alongside existing infrastructure; distros handle integration specifics.


## Cons

- **Base/distro boundary is hard to get right.** Too much in the base layer reproduces the current problem. Too little makes distributions non-interoperable with each other.
- **Ownership** is a pre-req. Maintaining a Distro requires ownership and commitment of maintainers. If ownership is lacking, the entire Distro model could not be realized.
- **Fragmentation risk.** Without strong base layer governance, distributions diverge and the ecosystem splits — the same failure mode as early Kubernetes distros before CNCF conformance existed.
